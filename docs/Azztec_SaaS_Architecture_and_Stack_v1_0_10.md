## 1. Purpose

Answer "FastAPI + React + what else?" with one opinionated, verified stack, the decisions behind it, the repo layout, and the
version pins — so the new chat builds instead of researching.

## 2. The shape

```
 Browser ──────────────► React SPA (Vite build)  ──── served by FastAPI app.frontend() in prod
                                │                      (Vite dev server + /api proxy in dev)
                                │ fetch /api/v1/...   (typed client generated from OpenAPI)
                                ▼
 FastAPI (uvicorn) ── routers ── services ── repos ── SQLAlchemy Core (sync) ── pyodbc ──► SQL Server  (dev: dbWorkmate = RST; dbWorkmate_KT = the KT oracle, read-only; dbWorkmate_KT_RFID = Ignition RFID dev copy, outside this build)
        │                │                            └────────────────────── psycopg 3 ─► PostgreSQL  (target)
        │                └── pure rules (planner/rules.py) — zero I/O, ported 1:1 from Ignition
        ├── /api/v1/ai/chat ──► workmate-ai (Layer 2 contract; same FastAPI service, own router)
        ├── diag middleware ──► stdout JSON + dbo.Diag_Log
        └── CLI (typer): `workmate nightshift`, `workmate planner nightly`  ← Task Scheduler / cron
```

Single process, single origin. No CORS in prod, no iframe, no HMAC `sid|uid` gate — a server-side session is the actor: the `azztec_session` cookie, its SHA-256 in `dbo.Auth_Session`, the person's `Users.User_Id` (D-5, OD-97).

## 4. Decisions

| ID | Decision | Rationale / consequence |
|----|----------|--------------------------|
| **D-1** | Monorepo `azztec-saas/` (`workmate-saas/` until October 2026) with `backend/` (uv project) and `web/` (pnpm project); one version tag per slice | one PR = one slice; the generated client lives next to the API that defines it |
| **D-2** | **Sync SQLAlchemy Core + `def` endpoints** (FastAPI threadpool) for phase 1; async only once PG-only | pyodbc is sync; `aioodbc` is fragile; a plant CMMS is tens of users; same Core code runs on both dialects; `def` endpoints run in anyio's threadpool (default 40 threads) — never do DB I/O in `async def`. When SQLAlchemy 2.1 is final, `mssql+mssqlpython://` becomes a URL change. ## 6c. Request flow (sign-in, DP2 2026-11-07)

1. **No session.** The SPA boots; `__root.tsx` sends every path but `/signin` through `SessionGate`, whose `useSession` asks `GET /api/v1/auth/me`. No cookie → 401 `NO_IDENTITY` → the cached session is `null` → `navigate('/signin', { next: <where they were> })`. Nothing behind the gate renders and no page query fires.
2. **Sign-in.** `POST /api/v1/auth/signin {login, password}`, carrying `X-Azztec-Request: 1` from the client's request interceptor. `require_csrf` runs first; then `service.sign_in`: the lockout counts from `Auth_Event` (by `Login_Key` and by address, the window's edge bound from Python) → `USER_BY_LOGIN` (exactly one active user; an unknown login is verified against a dummy hash, so both 401s cost the same) → the MD5-20 compare in constant time → the refusals in order → a session: 256 random bits, `Auth_Session` keeps the SHA-256, and `SIGNIN_OK` lands in `Auth_Event` in the same transaction. 200 `SessionInfo` (`user`, `rights {planner, womaint}`, `isAdmin`, `expiresAt`) and `Set-Cookie: azztec_session=…; HttpOnly; Secure; SameSite=Strict; Path=/`. A failure is 401 `SIGNIN_FAILED` (one body), 403 with the reason as its code, or 423 `LOCKED` — each one `Auth_Event` row and a `[G]`. The page shows the server's own line; on success `rememberSession` caches the session and drops every other query, and `/signin` replaces history with `next` (or `/planner`).
3. **Every request after.** The browser sends the cookie; `deps.get_principal` calls `LOADER` (`service.principal_from_request`): the `Auth_Session` row by hash, joined to `Users` → `session_state` (`revoked`, `expired` at 12 h, `idle` at 4 h, `ok`) and `Active`, every time → rights from the 60 s cache or `SECURITY_GROUP` + the menu tags → one `Principal`, however many gates ask. The router gates — `require('planner', 'RO')`, `require('womaint', 'RO')`, and on `_diag` the dev-only check then `require_admin` — answer 403 `NO_RIGHT`. `request.state.actor` is the principal's id, so the middleware's `[F]` line names the person. Last-seen is touched at most once a minute.
4. **The end of a session.** Sign-out: `POST /auth/signout` revokes the row, writes one `SIGNOUT`, clears the cookie, answers 200 `{ok:true}`; the web sets the session to `null`, drops every query, and the gate goes to `/signin?next=`. Expiry, idle, `Active = 'N'` or no group: the first request that finds it revokes the row, writes one `EXPIRED` with the reason (`expired`, `idle`, `inactive`, `no_group`) and answers 401; the response interceptor forgets the session and the gate does the rest. A replayed cookie after either is 401 and writes nothing.
5. **What the screen shows.** `ShellLayout` reads `pageAccess(rights, activeKey)`: RO puts a gold "view only" under the name; NA renders `NoAccess` in place of the page. The backend refuses regardless (D-5): a hidden control is a convenience, never the security.
6. **Measured** on `dbWorkmate_DP1_Test` (DP2a 25/0, DP2b 15/0; log 2026-11-07 §4): the cookie 43 characters with every flag; last-seen moved after 61 s; five 401s, then 423; a read-only session expired on the server sent the next click to sign-in and, after it, back to the same work order. The test password appeared in no table and no output.

## 9. Alternatives considered (so they are not re-litigated)

- **Next.js / SSR** — a plant CMMS is an authenticated SPA; SSR buys nothing and complicates on-prem hosting.
- **SQLModel / full ORM** — 227 legacy tables with `char(n)` keys and stored-proc write paths; Core + `text()` keeps the SQL greppable and dialect-tagged.
- **Async everything** — blocked by pyodbc; revisit at PG-only with `psycopg` async or `asyncpg`. The cost is visible now (OD-30): the server cannot cancel a request the browser has abandoned.
- **Celery/Redis** — no queue workload yet; Typer + Task Scheduler is enough.
- **FullCalendar** — resource-timeline views need the premium licence; the planner grid is custom anyway (as it is in `Planner_v1_8_1.html`, and now in `PlannerGrid.tsx`).
- **Keycloak/Authentik now** — phase 2; the legacy `Users` table is the identity source of truth until then.
- **A JWT session, or `App_User` with argon2, for the first drop** — the 1.0.0…1.0.9 plan, revised by OD-96 / OD-97 (2026-11-06): a JWT can't be withdrawn at sign-out or deactivation without a deny-list, and a second password store is one more thing for a client to run. Phase 2, with OIDC.
- **Carrying KT's Ignition-era tables verbatim** — `Ignition_User_Map` and `Ignition_Onboarding_Prefs` are keyed on Ignition usernames; the SaaS keys on its own logins, so the *shape* crosses (D-5) and the tables do not (KT Schema Delta §4.2). The 25 junk tables, the orphans and the `forecast` schema never cross.
- **Carrying KT's routines with the uplift** — `fn_Diag_UserTrail`, `vw_Diag_Problems`, `vw_Diag_WhoIsOn`, `wmsp_External_ContractorInsertUpdate` stay KT's (OD-42, 2026-09-14): T-SQL bodies are not portable, the SaaS reads none of them, and a view over an empty table is decoration. `0001` carries tables, columns, keys, checks and indexes only.
