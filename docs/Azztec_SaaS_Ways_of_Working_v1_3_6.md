## 1. The build cycle (unchanged)

```
audit → spec → 🤙 → build ONE slice → versioned raw file(s) → smoke-test → raw log → 🤙 → next slice
```

- Spec before code for anything structural. The chunk specs (`S1a`…`S1j`) are the template.
- One slice at a time. A slice is done when its smoke passes **on the RST dev DB** and the test half is green.
- 🤙 is the only gate. "Looks good" is not 🤙 — and neither is "sounds good, do what you think works best". That happened on OD-35 (2026-09-13) and it was recorded as **delegated, not signed**: the build went ahead on the proposal as written, and the record keeps the distinction because it is the OD with a downstream consequence (an expected parity diff). Delegation is a valid way to take a decision; calling it a signature is not.
- **The audit may cut the scope it was handed.** A proposal in a raw log's "next slice" section is an input to the audit, not a decision. Say plainly what is being dropped and why, and where it goes instead.
- **An unsigned decision cannot be smuggled inside a build slice.** If a proposed slice depends on something that has never had a 🤙, that dependency is the first line of the next audit — not a step in this build.
- **A decision about data is blocked on reading the table, not on 🤙** (§5). An OD whose correctness depends on what a table holds carries the pasted rows in the spec before it is signed.

## 2. What a deliverable looks like now

The repo is git-versioned, but the chat still hands over **files**, not diffs:

| Rule | Detail |
|------|--------|
| One file per Download card | delivered via `present_files`; never inline; never zipped |
| Versioned filename | `Azztec_SaaS_<thing>_vX_Y_Z.<ext>` for docs/scripts; backend code delivered as `Azztec_SaaS_app_<path>_vX_Y_Z.py`, frontend code as `Azztec_SaaS_web_<path>_vX_Y_Z.ts` / `.tsx` / `.js` (`Azztec_SaaS_web_lib_dates_v1_0_0.ts` → `web/src/lib/dates.ts`), each dropped into the canonical repo path |
| Version inside the file | Python: `__version__ = "X.Y.Z"` + header comment; TS/TSX/JS: `export const VERSION = "X.Y.Z"` + header (config files too — an extra named export is harmless to ESLint, Vitest and hey-api). **Exception: `src/routes/*.tsx` carry the version in the header comment only** — any export other than `Route` defeats code-splitting (Landmines §C); SQL/MD/PS1: header block, **PS1 ASCII-only** (Landmines §A) |
| Never overwrite | a change is a new version; the previous file stays in the chat history; git keeps the repo history |
| Header block | file, version, target path, author, spec reference, changelog newest-first |
| Bump rules | patch = fix, no contract change · minor = new function/route/field · major = contract break (route shape, JSON key rename, DB DDL) |
| The `__version__` constant is bumped with the header | or `/api/v1/health` lies — and it must **read** those constants, never restate them as literals. **Checked mechanically before any card is emitted:** parse the header's `Version:` line and the file's `__version__` / `VERSION` constant out of every delivered file and assert they agree. Two S1h files (`repo.py`, `schemas.py`) left the editor with `1.1.0` in the header and `1.0.0` two lines below it; a scripted comparison across all five modules caught both before the cards existed — reading did not (log 2026-09-13 1.2.0 §6.2); run across all fourteen S1i cards, all fourteen agreed |
| **The exported OpenAPI document is named from `main.__version__`** | `docs/api/openapi_<main.__version__>.json`, and its `info.version` *is* `main.__version__` — so a published-schema change with no app bump **is** a bump (OD-38, 2026-09-14: `Priority` gained a required `colour`, `main.py` 0.3.0 → 0.4.0, `openapi_0_3_0.json` → `openapi_0_4_0.json` as a git rename in the same commit, `openapi-ts.config.ts` input bumped, `pnpm gen:api`). Minor for a new field, patch for a re-wrap. Never regenerate in place; never leave two contract files on disk; export from `app.main.app`, never a second `create_app()` |
| **Every delivered file is marked PK or not** | the card says whether it goes into project knowledge, and which version it supersedes. A card whose target filename has an extension project knowledge refuses (`.mako` — "Add to project" greyed out) ships a byte-identical `.txt` twin for PK, decided when the card is cut, not after (log 2026-09-14 1.1.0 §6.4) |

**Git mapping.** After the smoke passes: `git add -A && git commit -m "planner rules 1.1.0 — S2 moveRules"` and tag slice completions `git tag s2-move-1.1.0`. **Tag the version that shipped, not the version the spec predicted** — a mid-slice patch bump changes the tag (S1g's spec said `planner.css` 1.1.0; 1.1.1 shipped; the tag is `s1g-readonly-1.1.1`). One commit per delivered file set. Never rewrite pushed history.

**Dropping files is a step that can fail.** `Unblock-File` in `Downloads` is not a copy. Every drop block lists the exact filenames it expects, and after the drop `Test-Path` each target **by that exact name** — a wrong name has the right `Length` (`range.fictures.ts` was the one hand-typed name out of 22 and only the failing import caught it). Then check `Length` and `LastWriteTime` on the **target**, and grep `^__version__` before running anything. A smoke that reproduces the previous failure byte-for-byte is evidence the drop failed, not that the fix failed. **The verification line is the evidence, not the copy's silence:** a drop block re-run after its sources had been moved out of Downloads copied nothing and said nothing; only `Test-Path`/`Length` on the targets showed the files were already on disk. **And Downloads is not a staging area:** a card is on disk only once it has been saved — the S1g spec was presented at the audit and saved hours later, so the docs copy in the commit block silently missed it and `git add -A` committed the slice without its spec (fixed in `0cb41b8`); the next session the five compiled-doc cards were presented and the laptop rebooted before they were saved, caught only by the alphabetical gaps in a Downloads screenshot; the session after that the S1h spec was never saved and the slice commit carried eight files instead of nine (`85d4e95` carried the ninth). Three consecutive sessions. Save every card before the block that copies it runs, and **every block that copies from Downloads begins with `Test-Path` on each source and prints it** — a missing card fails on line one, not two screens later. **Fourth session, held:** fourteen S1i cards and the spec went through such a block and the slice commit carried all seventeen paths (`e0a3501`). **Fifth, held:** eight S1j cards plus the spec, ten paths in `f851889`. Keep it.

**Verify before you commit.** A gate you write and don't enforce is not a gate. On 2026-09-13 the plan was suites → commit with "if the counts match, commit" written into the step; the suite block returned nothing and the commit ran anyway — for twenty minutes the repo asserted today's counts on yesterday's evidence (log 2026-09-13 1.1.0 §4.1). **A verification that returns nothing is a failed gate, not a passed one.** Read the result, then commit. And shape the verification line so it can answer: PowerShell formats a second object type with the first one's table and silently drops the columns it has no header for (Landmines §A) — `Format-List` the verification line, or run it in its own block. **And predict the staged-path count:** the S1i commit block expected 18 paths and 1 deletion and refused — git had recorded the contract export as a 99 % rename (17 and 0); the prediction was wrong, the gate caught it before the commit, and the lineage is better recorded for it. **And a verification query must not be satisfiable by data it was not asking about:** the S1j smoke's `new_cols` check counted column names across nine tables, and MSSQL matched three pre-existing legacy stamps case-insensitively — 18 where 15 were added. The migration was right, the query was loose, and the per-pair assertion in `test_kt_uplift` was the real gate (log 2026-09-14 1.1.0 §6.3). Write the check so only the thing you are asserting can satisfy it.

**Format-clean before commit — `ruff format .` repo-wide, not `ruff check` per file.** E501 is in `pyproject`'s ignore list, so a long line passes `ruff check` forever; S1h's per-file check-only smoke shipped `router.py` one character over `line-length = 110`, and the S1i format pass found it a session later as a fourteenth modified file against thirteen cards. The format step is the gate, the check step is the lint, and the order in §6 is the order (Landmines §A). The fix shipped as `router.py` 1.1.1 format-only — flagged before it was built, the `test_planner_repo.py` 1.0.2 precedent: the file on disk must not silently differ from its project-knowledge card.

## 3. File types

| Kind | Format | Notes |
|------|--------|-------|
| Backend code | `.py` — 4-space indent, Ruff-formatted, type-hinted | f-strings only (UP031) and `Annotated[T, Depends(...)]` only (B008), from the first draft |
| SQL | lives **inside** `backend/app/<module>/sql.py` as `text()` constants | carries the NQ-style header: name, dialect line, PG-CONVERT tags. The CI gate greps the **whole file** — describe banned tokens, never spell them. A standalone `.sql` only for DDL run in SSMS or `sqlcmd` |
| Migrations | `backend/alembic/versions/*.py` | only for objects Workmate adds (the twelve KT-parity tables, the fifteen columns, …) — never `--autogenerate` against the legacy 227 tables (`env.py` has `target_metadata=None`). **Generated, committed static, diffed by a test:** `0001_kt_parity_additive` is rendered by `scripts/kt_uplift_ddl.py` from `dbWorkmate_KT`'s catalog (never typed), committed as a reviewed file, and `test_committed_migration_matches_the_kt_catalog` re-reads the oracle and asserts byte equality (S1j, 2026-09-14). The migration carries two renderings of one catalog chosen by `conn.dialect.name` — not `-- PG-CONVERT:` tags, which are for `sql.py` statements (OD-46). `alembic upgrade head --sql` is its `DRY_RUN` (§6) |
| Frontend code | `.ts` / `.tsx`, strict TypeScript, Prettier, `@tanstack/eslint-config` | generated API client (`src/api/client/**`) is never hand-edited **and never linted** — `eslint.config.js` ignores it, and the generator post-processes with Prettier only |
| Tests | `backend/tests/test_<module>_<slice>.py` (pytest), `web/src/**/*.test.tsx` (Vitest), `web/e2e/*.spec.ts` (Playwright) | pair rule: a library slice ships with its test file |
| Docs | `.md` in `docs/` and in project knowledge | raw logs append-only |
| Scripts | `.ps1` (Windows dev), `.sh` (appliance/Linux) | idempotent, print what they did |

## 4. The pair rule, with teeth

- `rules.py` (pure) → `test_planner_rules.py` runs with **no database** (plain dicts).
- `repo.py` / `service.py` (DB) → tests run inside a transaction that is **rolled back** (`conn.begin()` … `rollback()`), so the RST data is never mutated by a test. Marker Law still applies to anything that commits.
- Every write function keeps the Ignition signature idea: `dry_run: bool = True` default, `expect_start_iso` optimistic lock, returns a dict/model, never raises past the service boundary.
- **A test written zero-DB must actually be zero-DB.** Check the dependency graph, not just the assertion: a route that resolves `Depends(db.get_conn)` opens a connection before the handler runs. Zero-network means the stubbed `fetch` is asserted never called.

## 5. Fact-check before build

- A CLI flag is verified on the box before a script relies on it — `pnpm dlx @tanstack/cli@latest create --list-add-ons … --json` and `--addon-details <id>` pasted, not a README remembered. S0 lost `web/` to a flag that had stopped existing; S1e checked first and lost nothing.
- A scaffold or script that deletes must fail before it deletes, never after. Guard on the target existing, run the risky command, check `$LASTEXITCODE`, and only then touch anything else.
- Column names, status codes, flag domains, FK targets: verify against `All_Tables_InDetail.csv` and the RST DB itself (`SELECT TOP 5 …` via `sqlcmd -C` or SSMS, pasted). The RST DB is the same legacy schema but **its data domains may differ from KT** — probe, don't assume (Data Layer doc §5). Since 2026-09-13 KT's own database is on the box too (`dbWorkmate_KT`, read-only): when the two sites disagree, read both tables and say which one the claim came from.
- **The database says what exists; the gateway export says what is used.** A KT-only object is not load-bearing until it is grepped against the Ignition project export (1,986 views, 1,700 named queries, 382 scripts on the 2026-09-10 export). That is what exposed `Ignition_Tip_Definitions` as an orphan and confirmed the other twenty KT tables as live (KT Schema Delta §5.2). A DDL that crosses to RST is scripted from `dbWorkmate_KT`'s catalog at build time, never typed from a doc.
- **A decision about data is blocked on reading the table, not on 🤙.** OD-32 (priority badge colour by rank) was proposed from a chip screenshot, signed, built, shipped and withdrawn the same day: five minutes of `SELECT` on `dbo.Priority` — fourteen rows, four tied at `Sort_Sequence` 1, so the tie-break ranks P2 ahead of P1 — would have killed it at the audit. Any OD whose correctness depends on a table's contents carries the pasted rows in the spec before it is signed. One build cycle, once.
- **Say "the API doesn't send it", never "it isn't there".** Absence from an API shape is not absence from the database: `/range` sends `{id, short, title}` for priorities while RST's `Priority.Colour` is populated and varied. The honest sentence names the layer that omits the thing.
- Anything the Ignition planner computes is the parity oracle: same window, same DB → same `counts`.
- **Never re-emit a file you have not read.** Reconstructing a shipped module from its spec silently reverts whatever the spec did not describe. Ask for the current source; the cost of asking is one paste. This includes files a CLI wrote: read `eslint.config.js` before replacing it, and read the generated client's `^export` lines before writing anything that imports them. **It includes the oracle's strings:** `rules.test.ts` 1.0.0 asserted `Monday 14 Sep 2026` from memory in four places where the oracle's `fmtLong` builds `Mon` from the abbreviated DOW. Strings are parity surface — read the oracle line, then pin it. **And it includes column names:** `Short`/`Title` cost a round trip on 2026-09-13 when `Short_Priority_Id`/`Priority_Title` were in `sql.py` 201–204 — a file already in project knowledge and already read that session. A column list from memory is a file from memory, priced at one round trip instead of one build.
- **A knowingly false header is never the price of a scope line.** A spec that says "seven files, no eighth" is a scope line, not a licence to ship a stale pointer: when a change makes a `Pair:` / `Pair of:` line in a file the spec did not list go stale (S1h's `PRIORITIES` column made `repo.py` → `test_planner_repo.py 1.0.0` and that file's own `sql.py 1.0.1 + repo.py 1.0.0` both wrong), that file ships too — **header only, flagged before it is built, not slipped in** (`test_planner_repo.py` 1.0.2; log 2026-09-13 1.2.0 §6.4). Its assertions are re-run by hand against the new version so the header-only claim is a checked one.
- **Check the box before the code.** Before diagnosing any latency, paste free memory and the top-5 processes by working set (`Get-Process | Sort-Object WorkingSet64 -Descending | Select-Object -First 5 Name,@{n='GB';e={[math]::Round($_.WorkingSet64/1GB,2)}}`) — verbatim, before the first hypothesis. Four hours went into DMVs and request timing while Docker Desktop held 45 GB of a 32 GB box (Landmines §F). A smoke on a starved box measures the box, not the slice. When the box *is* clean and it is still slow, the first question is whether SQL Server has been **restarted** since the squeeze: item 30 turned out to be a squeezed instance faulting its buffer pool back in for hours after `Get-Process` read clean — free RAM is not a recovered buffer pool (Landmines §F). Restart, then measure; the DMV pattern that attributes what remains is in Architecture §3.3.

## 6. Smoke-testing

Every slice has a written smoke line in the spec. Minimum, **in this order**:

```
uv run ruff format .                          # load-bearing, repo-wide: ruff check cannot catch what ruff format fixes (E501 ignored)
uv run ruff check .
uv run pytest                                 # backend green — bare: NO -q (pyproject already sets addopts="-q"), read the count, check $LASTEXITCODE
uv run fastapi dev app/main.py                # boots, /api/v1/health returns version + db ok
curl "http://localhost:8000/api/v1/planner/range?from=2026-09-14&to=2026-09-20"
pnpm --dir web test && pnpm --dir web build   # frontend green + builds
```

Frontend order when the slice touches `web/`: `pnpm gen:api` → `pnpm lint` → `pnpm test` → `pnpm build`, then `gci web\dist\index.html`. `pnpm lint` is **ESLint only** — `prettier --check` (the CLI's `check` script) is not in the smoke yet; add it to this order or say why not (open item 25). **Any slice that creates or changes `web/dist` re-runs the backend suite and the dev-server request set with `dist/` present** — the mount flips behaviour without a backend file changing (Landmines §A).

**Three windows.** Backend, Vite and the command shell are three PowerShell windows. Any block that starts a server does it with `Start-Process powershell -ArgumentList '-NoExit','-Command','cd C:\dev\workmate-saas\backend; uv run fastapi dev app/main.py'` (same shape for `pnpm --dir web dev`) so it cannot land in the window the other server lives in — S1f lost twenty minutes and three false "it's broken" readings to servers trading places. Vite is on **`:3000`**, the backend on `:8000`; a port check tries both `::1` and `127.0.0.1` (Landmines §C). Close stale browser tabs before judging a fix by the Vite console — a `[Client]`-prefixed warning is a tab talking, not the server. **One browser tab during a smoke** — two planner tabs both poll `/range` every 60 s, which doubles the load and makes the timing lines in the dev-server log useless (log 2026-09-13 §4.5). **And wait for the prompt before pasting the next block** — a block pasted while the previous output is still scrolling overprints the echo; the file on disk is fine, the paste record is not (log 2026-09-13 1.1.0 §4.8).

**Before the smoke, the box.** If the machine shares RAM with Docker Desktop, free memory first (§5, Landmines §F). A `/range` over 2 s is the box until proven otherwise — and a clean box that is still slow is open item 30, not a reason to skip the check.

Console output is pasted verbatim into the chat before the next step. **The dev-server terminal is part of the smoke, not decoration** — the `[F]`/`[G]` lines are where a slice proves it did what it claimed, and the `[F] range …` lines that complete after the user has clicked away are OD-30 working, not a leak.

**Predict the count, then read it.** Write the expected test count into the step before the run — per file from the cards' own `it()` counts, or "unchanged" when the cards are version lines — and read the run against it. 170 frontend was predicted per file for S1i and every number matched; 156 backend was predicted *not* to move and did not, which is what proved three cards were header-only. A count read without a prediction is a number; a count read against one is evidence. The same for the smoke's wire lines: `libVersion` was predicted 1.2.0 and read 1.1.0 — `libVersion` is backend `rules.py`, not `rules.ts`, two modules with one stem and one wire field; the prediction was wrong and writing it down is what caught it.

**`--dry-run` is the default verb, not a flag you remember.** Anything that writes — a generator, a migration, a service call — writes nothing unless told to (`--write`, `dry_run=False`, `alembic upgrade head` after `--sql`), so the first run is always a read. Read the render before writing it: the S1j generator's first dry run showed a hash-named PK and a `numeric` identity PG would refuse, both fixed as generator 1.0.1 with OD-46a / OD-46b raised and signed before anything reached the tree (log 2026-09-14 1.1.0 §4.3). A wrong rendering is a new version, never a committed file you know is wrong.

Count tests from the run, never from the previous raw log; the number drifts as files gain cases. **Run both suites bare and gate on the exit code.** Plain `uv run pytest` — `pyproject.toml` already sets `addopts = "-q"`, and a second `-q` on the command line deletes the `N passed` summary line (three sessions blamed the pipe — `-Last 3`, `-Last 6`, `Tee-Object`; Landmines §A) — then read the count with your eyes and print `$LASTEXITCODE`. Plain `pnpm test` the same way: its summary is box-drawn and ANSI-coloured, so `Select-String "Test Files|Tests "` matched nothing, printed blank and returned to the prompt looking exactly like a clean run (log 2026-09-13 1.1.0 §4.2) — the filter was wrong, not the run. **Never gate on a `Select-String` whose pattern is a guess; pipe only when the exact output text is already known.** The exit code gates the commit; a commit whose log cannot show the count is a commit with a hole in it. **A skip is part of the count.** Every DB-dependent test skips with its reason in the message, never passes quietly, and the summary is read as `N passed, M skipped`. Since `0001`, backend is **169 passed, 2 skipped** — the 2 are `test_planner_repo.py`'s OD-1 tests retiring themselves now `WO_N_Plan` exists: `0 skipped` means the migration did not land in the database the suite points at, and a third skip means the KT oracle was unreachable and the catalog gate silently did not run.

**A test whose pass depends on which database it is pointed at is a data assertion wearing a port assertion's clothes.** `test_range_priority_order_is_not_alphabetical` was true on RST (P2, P1, P3, P5, P6, P4, N/A) and false on KT, whose A / B / C / D legitimately *are* alphabetical — it would have gone red against a perfectly good database, two hours after the S1h spec's own warning that *seven rows is one database's state on one day, not a contract* (log 2026-09-13 1.2.0 §6.3). Assert the port instead: a control query compared through `repo → service → schema → JSON` proves nothing can quietly reorder, on either database. The one permitted RST-shaped assertion is about a missing table (`test_range_pin_table_false_on_rst`), not a data count or a data order — and every such test names the database it assumes in its docstring.

### 6.1 The trail read — every test ends with it (standing rule, 2026-09-16)

**Every test ends with the trail:** the test identity's rows over the test window, pasted verbatim, compared line by line with the predicted trail written in the spec's smoke section *before* the run. An unpredicted `[G]` or `[E]`, a missing `[F]`, or a row with no user is a finding before the commit — never after.

- The reader is `scripts\Show-DiagTrail.ps1 -UserId 21 -Minutes 15 [-ProblemsOnly]` (D1a). Before D1a it was the backend window's JSON lines, tee'd to a file with `PYTHONUNBUFFERED=1`.
- **Wait two seconds** after the last action before reading — the writer batches for one, and a row logged in the same second as the read is not yet a row.
- The trail says what the code logged, not what the screen shows; screenshots stay for layout, and pixels are measured rather than eyeballed (S1k: the underline, the gradient, the dialog dim).
- Predict the trail the way the test count is predicted: write it down, then read. Its first two uses caught an actor gap, an orphaned process, a batch-ordering quirk and a 422 — none of which a green suite showed.

### 6.2 Process hygiene the smoke depends on (2026-09-19)

- **Stop the server before a drop, or expect the reload to be the first smoke.** `fastapi dev` picks the files up as they land.
- **Stop the server child, not the reloader**, and **prove exactly one PID listens on 8000** before trusting any response (Landmines §A) — killing the reloader orphans a child that keeps serving with stale settings.
- **Smoke, then commit — never the reverse.** D1a's commit ran while the smoke's last step had not read as predicted; the suites were green so the tag stood, and the proof came ten minutes later. It is recorded as a mistake because the order is the rule.
- **The drop block:** `Test-Path` every source first with a normalised-name fallback (a browser may rename a download), copy nothing if one is missing, `Unblock-File` every `.ps1`, check header version against constant, then `git status --short -uall` — the predicted path count is part of the spec.
- **`pytest` runs are not allowed to write to RST.** Persistence is off under `WORKMATE_ENV=test`; a Marker Law case in `test_kt_uplift` names the tables the product fills by design and asserts every other crossed table is empty.

## 7. Diagnostics discipline

`Workmate_Forensic_Diagnostics_Standard_v1_1_0.md` carries over. Implementation: `app/core/diag.py` — one `log(level, message, detail, actor)` that writes structured JSON to stdout **and** persists to `dbo.Diag_Log` (async, never blocks, never raises), wired by `diag.configure()` from the app factory. Every route outcome is one [F]/[G]/[E] line with the request id. `/api/v1/_diag/self-test` replaces `/planner/_echo`. The persist half now has a contract to meet: KT's `dbo.Diag_Log` DDL (KT Schema Delta §4.1) — `Session_Id`, `Source`, `Tier`, `Msg_Level` NOT NULL — and what fills them from the `[F]/[G]/[E]` seam is answered by KT's own data (OD-47, recorded not signed: `Tier` = the tag letter, `Msg_Level` = the level word, `Source` = the emitter, `Session_Id` = the request id) and becomes an OD in the persist slice's spec; `dbo.Diag_Log` exists on RST since `0001`, empty.

**The instrument law.** A diagnostics test that asserts the **return value** of `diag.log()` is not a diagnostics test — it proves the function was called, not that anything was emitted. The same goes for a health field that reports where records *would* persist. Both of those passed for three slices while every `[F]` and `[G]` line was being discarded at the logger's level check.

- Assert **emission**, at the stream, with `capfd`. Not `caplog` (its handler is on root and it proves the call, not the write). Not `capsys` (it swaps `sys.stdout` at the Python level).
- A wiring check tests the specific handler by name — never `hasHandlers()`, which any test harness satisfies.
- Report wiring and persistence as two separate facts (`diagWired` and `diag`).
- Generalise: when a test and the real path disagree, assume the real path is right and the test is the thing that is wrong.

## 8. Comms

- Short, direct, NZ-casual. Surgical steps. No preamble.
- Shell blocks are complete and copy-pasteable, never hand-typed: each starts with `cd C:\dev\workmate-saas…` (a fresh window opens in `system32`, Landmines §A), names the exact files it expects to find, and is ASCII-only when it is a `.ps1`. One block, then the prompt, then the paste, then the next block.
- Paste console output; screenshots for UI review; defects fixed immediately.
- Decisions get an ID (D-n in architecture, OD-n open decisions in specs) and a date. A decision that is withdrawn keeps its ID, struck through, with the reason — OD-32 is the precedent; the number is never reused.
- Close a session with `Azztec_SaaS_Raw_Log_YYYY-MM-DD_vX_Y_Z.md`: decisions, mistakes caught, patterns confirmed, facts verified — dated one-liners. **A superseding log must carry forward every open item it does not close.** An item that silently drops out of the open list is worse than an item left open: 1.0.0 §8.1 named the web-toolchain decision "the oldest open item" and 1.1.0 lost it entirely.

## 9. Knowledge maintenance

Two layers as before: **raw** (dated logs, schema CSVs, the Ignition sources, `.NET` manuals — never rewritten) and **compiled** (this set — versioned, edited, kept sharp). Four writing rules: one lesson per section; update, don't duplicate; delete what's wrong (note it in the changelog); never touch raw. Platform claims carry a verified date; anything older than a major version bump of that platform is re-verified before being relied on.

**Project knowledge is a third obligation, not an afterthought.** The chat surface cannot read the repo — only project knowledge. Every delivered file therefore goes into project knowledge at its current version, and the superseded version comes out. When it doesn't, the next audit reconstructs from a spec instead of reading the code, and reconstruction reverts whatever the spec didn't describe.

- Each card states **PK: add / replaces `<old version>`**.
- At session close, the raw log ships **with** the doc updates it implies — Landmines, this file, the Index. The next session's first task is that doc set, applied before any audit, each file read in full before it is re-emitted; the audit then reads the docs, not the log.
- The Index §3 file table is the inventory: if a file is live in the repo and absent from that table, it is missing from project knowledge. The reverse holds too: a superseded version still sitting in project knowledge is the one the next audit reads by mistake — the Index §6.2 names what to remove, and the first task of a session is to check that list against the project files, not against the log.
- Evidence that is not a decision stays labelled as evidence. The KT Schema Delta is "evidence complete, nothing signed" and its §8 questions are numbered as questions, not ODs, until an audit signs them.
